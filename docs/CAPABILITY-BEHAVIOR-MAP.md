# FloatCTF 前端「行为语义地图」（Capability Behavior Map）

> **用途**：为从零实现的 **新可插拔前端**（`frontends/floatctf-frontend-xzmu`）提供一份「不必逐个读 107 个 Default route 文件」的行为语义参考。
> **权威基准**：[`docs/frontend/CAPABILITY-MATRIX.md`](../../../docs/frontend/CAPABILITY-MATRIX.md)（127 行能力，其中 **89 行 `required`**）。
> **本文只覆盖 `required` 行**：`optional` / `specialized` 行不在范围内（「管理端：基础设施、系统与平台设置」章 0 项 required，仅列出清单作说明）。
>
> **读法**：每章一张表，一行 = 一项 required 能力。表的列对应实现者要回答的 8 个问题：调哪些 SDK、依赖什么状态、有什么权限边界、哪些是破坏性操作、三态渲染什么、怎么刷新。
> 表下每项能力有一段要点（数据依赖链 / 状态取值语义 / 证据行号）。
>
> **硬约束（来自 CAPABILITY-MATRIX 与 AGENTS.md）**：
> - 新前端只能依赖 `@floatctf/sdk` + `@floatctf/frontend-runtime`（React 才可选 `@floatctf/react`）；**禁止** import `frontends/default/*`、`apps/web/*`、`packages/*/src/*`。
> - 本文中的 `frontends/default/...` 路径**只是语义证据**，不是可 import 的 API。
> - 只记录**从源码读到的事实**；推断显式标注「推断」并给出依据。
> - 不描述 Default 的视觉 / 布局 / 导航 / 路由结构。`Default 参照文件` 列只用于定位语义。
>
> **证据格式**：`相对仓库根路径:行号`。所有行号基于本仓库当前工作区状态。
> 同一能力块内的**短引用**（如 `scoreboard.tsx:32`、`Table.tsx:298`）指该行「Default 参照文件」列点名的文件，或同一句/同一段中已给出完整路径的文件；跨文件引用一律写相对仓库根的完整路径。校验方式见文末「覆盖率自查」。

**要点**

- **公开引导元数据**：`GET /api/frontend` 的取数、解析、前端选择、兼容性校验**全部由平台 bootstrap 完成**（`packages/frontend-runtime/src/bootstrap.ts:163-190`）。新前端的义务是正确实现 `mount(context)` 并消费已解析字段（`bootstrap.ts:295-306`）；自行再读该元数据属可选增强，不计入完整性。`capabilities` 是平台声明的能力字符串数组，元素由平台决定，前端只做「按需探测」，不要硬编码为唯一真值（`module.ts:32-33`）。
- **前端挂载契约**：`FloatCTFMountContext` 字段清单与语义见 `packages/frontend-runtime/src/module.ts:16-34`：`apiBaseUrl`（同源 API 前缀，例如 `/api`）、`assetBaseUrl`（本制品资源根，用于加载自身图片/字体）、`platformVersion`/`apiContractVersion`/`frontendRuntimeVersion`（诊断用）、`capabilities`（只读字符串数组）。新前端应以 `context.apiBaseUrl` 构造客户端（`createFloatCTFClient({ baseUrl: context.apiBaseUrl })`），**不要**硬编码 `/api`（参考 `frontends/default/src/dev.tsx:9,18` 用 `DEFAULT_API_BASE_URL`）。
- **契约版本常量与兼容性判断**：`FRONTEND_RUNTIME_VERSION = "1"`、`API_CONTRACT_VERSION = "1"`（`version.ts:14,17`）。`isMajorCompatible(constraint, current)` 用于判定 manifest/注册表里的 `compatibility.frontendRuntime` / `apiContract` 是否与当前平台一致（`paths.ts:119-129`）；bootstrap 的选择逻辑在 `bootstrap.ts:272-280`。新前端在打开时若需要自检，应消费 `context.apiContractVersion` / `context.frontendRuntimeVersion` 而不是重新请求。
- **统一响应封装与成功码**：`code` 是平台业务码，`0` 为成功（`protocol.ts:5-7,32`）。SDK 的领域方法返回的是 `response.data`（axios 响应体），即 `UniResponse<T>` 本身，所以使用方式是 `const res = await client.service.events.fetch(); res.data`（对照 `packages/sdk/src/api/service/events.ts:17-22`）。列表 `meta` 的权威形状是后端 `{total, page, limit}`（Default 的 `PaginationResponse` 定义 `frontends/default/src/components/Table.tsx:41-44`，读取 `Table.tsx:298`）；`QueryParams` 另含 `offset`（`protocol.ts:15-21`）。
- **统一错误模型**：`FloatCTFError` 保留 axios 兼容形态（`error.response?.data?.message`）以便迁移，同时提供类型化字段（`errors.ts:5-12,27-33`）。非 2xx 走 `http`，2xx 但 `code!==0` 走 `platform`（`errors.ts:161-175`），无响应走 `network`（`errors.ts:153`）。Default 的 `formatApiError` 是**展示层**口径，可参考但不必照抄（新前端自己的 dialog/toast 体系）。
- **SSE 传输原语**：`client.sse.connect` 用 fetch + ReadableStream 而非 `EventSource`，因为 `EventSource` 不能带 `Authorization` 头（`connectSse.ts:1-6`）；token 永不进 URL。重连采用指数退避 + 抖动，401/403 停止重连（`connectSse.ts:7-12`），`Last-Event-ID` 由 `lastEventId` 选项驱动（`connectSse.ts:124-127`）。React 侧的通用模式是「连上停轮询、断开启轮询」（`useAwdEventStream.ts:126-146,157-175`）——非 React 前端应自行复刻这一对偶语义。

**要点**

- **`GET /events` 的 `hidden` 不是前端过滤**：后端 `WHERE hidden=false AND is_virtual=false`（`apps/api/src/modules/event/common/api/player.rs:39-40`）。矩阵里的「含 `hidden` 过滤」= 后端保证隐藏赛事不出现在选手列表；单条详情同样把 `hidden=true` 当 404（`player_service.rs:190-194`）。
- **赛事状态（upcoming/ongoing/ended）完全是前端推导**，没有服务端 `status` 字段：`components/EventStatusBadge.tsx:10-26` 与 `jeopardy.$id/index.tsx:25-36`。而**加入/退出/建队的服务端时间判定**用的是 `event_time_status_of`（`NotStarted/Ongoing/Ended`，`player_service.rs:144-152`）。两者必须在语义上对齐：`upcoming` ≈ `NotStarted`，否则会出现「按钮可点但后端报错」。
- **`allow_join` 同时管「加入」和「退出」**（`player_service.rs:667-669,729-731`）：关闭报名后，Default 仍可能显示 Leave 按钮（它只看 `status` 与 `joined`，`:187-205`），后端会报「该赛事未开放退出」。
- **`purpose` 决定能否加入**：只有 `competition` 支持 join/team；`practice` 与 `system_key` 非空的事件一律 `UnsupportedForPurpose`（`player_service.rs:113-125`）。这与「AWDP 练习走 Training Ground run、不走赛事报名」一致。
- **`team_result` 只在详情接口有**：列表接口 `team_result=None`（`player_service.rs:175-181`）。因此「我在哪支队伍」必须用 `events.get(id)` 拿（`types/eventInfo.ts:19`）。
- **赛事积分榜/趋势是 30s 轮询，公告是 60s 轮询**（`scoreboard.tsx:32`、`trend.tsx:22`、`announcement.tsx:28`）——矩阵把这些标为「无实时」，新前端用轮询或手动刷新都合规，但**不能假设数据会自己变**。
- **赛事题目列表的服务端门槛最高**：`赛事已开始` + `joined` + `hidden=false`（`player_service.rs:250-271`）。所以「赛事详情页能进」不代表「赛事题目能看」——前者只要求时间不是 not-upcoming 且已加入（`jeopardy.$id/index.tsx:164`），后者额外要求赛事已开始。

**要点**

- **AWD 面板的主键是「队伍」而不是「用户」**：`status` 接口要求队员关系（`player.rs:548-551`），`banned` 是**队伍级** active ban（`:563-570`），`score` 是队伍总分（`:572-578`），`AwdScoreRow` 也是按 `team_id` 聚合（`awd.ts:138-145`）。先确保 `events.get(id).team_result` 有队伍，否则 AWD 各接口都会 403/404。
- **phase 取值与可用动作汇总**（证据：Default 的 `flagAllowed`/`resetAllowed` + 后端 `render.rs:186-232` 防火墙策略）：
  - `hardening`：网络只允许本队互通（跨队 DROP，GameBox 出网全阻断，`render.rs:187-213`）；**不能提交 flag**（`awd.$id/index.tsx:56-57`）；**可以 Reset**（`gameboxes.tsx:30`）；WireGuard/SSH 可用。hardening 由 `hardening_ends_at` 定时转 `attack`（`apps/api/src/modules/event/awd/scheduler/mod.rs:603-648`）。
  - `attack`：跨队可攻击、GameBox↔GameBox 与 flagserver 放通（`render.rs:215-225`）；**可提交 flag**（需 active round）；可 Reset；WireGuard/SSH 可用。
  - `pause`：网络双向阻断（`render.rs:227-231`）；不能提交 flag（`index.tsx:54-55`）；不能 Reset（`gameboxes.tsx:29`）；WireGuard/SSH 显示暂停警告。
  - 另有两个独立于 phase 的开关：`status ∈ {finished, archived}`（terminal）与 `final_settlement=true`（最后一轮结束但 Judge 仍在结算）——两者都禁止 flag / reset / WG / SSH，且 `final_settlement` 时排行榜仍可能变化（Default 文案，`awd.$id/index.tsx:313-318`）。后端 terminal 判定见 `api/player.rs:101-103,174-176`。
- **Reset 的免费次数不在选手端 DTO 里**：罚分规则是服务端算的（`reset_service.rs:190-199,406-424`，默认 `free_reset_count=3`、`extra_reset_penalty=100`，`event_service.rs:674-675`）。选手端只能按 Default 的措辞警示，**不要伪造「剩余 N 次」**。
- **提交 flag 的响应在 SDK 层被抹平**：后端 `SubmissionResponse` 含 `was_first_blood` 等（`api/dto.rs:387-393`），但 `client.awd.player.submitFlag` 的类型是 `UniResponse<null>`（`awd.ts:592-600`）。要展示一血提示只能靠随后刷新的积分榜/SSE，或使用逃生舱（`client.serviceHttp.post("/events/<id>/awd/submissions", ...)`，需在交付说明中声明）。
- **SSE 不能替代 REST**：事件只是「失效信号」，真正的数据仍来自 `status`/`gameboxes`/`scores` 等 REST 调用（`awdInvalidation.ts:1-10` 明确记录了这个设计原因）。

**要点**

- **AWDP `phase` 全取值与门禁**（证据：`apps/api/src/modules/event/awdp/service/event_service.rs:1-65`、`break_service.rs:36-94`、`patch_service.rs:181`、`evaluation.rs:43,1132`、`runtime.rs:121`）：
  - `pending`：run 已创建但未开始；无实例、不能提交 flag、不能上传补丁。
  - `break`：**只能提交 Break flag**（`break_service.rs:55` 要求 `phase == Break`）；补丁被拒（`patch_service.rs:181`）。
  - `preparing_fix`：**durable 过渡态**，系统把所有已启动实例 reset 到 pristine（`event_service.rs:23-65`）；此阶段 source 锁定、补丁禁止、Break flag 禁止。前端应把它当作「不可操作，等待自动进入 fix」，且**如实展示**而不是误报 `pending`（`apps/api/src/modules/event/awdp/api/player.rs:110`）。
  - `fix`：可上传补丁、可 Test Check、官方评测按回合运行（`evaluation.rs:43`）；Break flag 被拒（`break_service.rs:59`）。
  - `ended`：run 结束；只读。
- **Break 提交的三态结果要看 `accepted` 与 `scored` 两个字段**，不能只看 HTTP 成功：`accepted && !scored` 表示此前已攻破（`BreakSubmitResponse.already_broken`，`awdp.ts:64-68`；Default 分支 `AwdpWorkbench.tsx:336-346`）。
- **Test Check 的 `exploit_ok=false` 不等于修复成功**：只有真正跑出 exploit 结果时才有结论；Default 明确注释了历史上因此误导选手（`AwdpWorkbench.tsx:774-780`）。
- **`preparing_fix` 是关键易错点**：它不是「pending」，也不是「fix」；把它当成 fix 会让补丁上传按钮亮起但后端必然拒绝。
- **赛事模式不提供实例 Start/Stop/Get 的 UI**：实例到点自动启动（`AwdpWorkbench.tsx:598-601`），SDK 的三个方法在 Default 无调用点（`grep` 证据见上表）。新前端若要用它们，需自行确认后端 `runtime.rs:121` 的 `break/fix` 门禁。
- **积分榜/趋势/评测都是「轮询 + SSE 失效」双通道**：`scoreboard.tsx:32`、`trend.tsx:25` 各有 30s `refetchInterval`，而 SSE 失效列表在 `useAwdpEventStream.ts:58-65`。

**要点**

- **admin 赛事列表返回全部赛事（含 `hidden=true` 与 `is_virtual=true`）**：与玩家端 `GET /events` 的 `hidden=false AND is_virtual=false` 过滤（`apps/api/src/modules/event/common/api/player.rs:39-40`）形成对照。管理端必须能看到隐藏赛事。
- **`is_virtual` 是「平台自有赛事」标记**：admin 详情页对它只开放 Instance/Logs（`routes/admin/events/jeopardy.$id/route.tsx:54-68`），后端也禁止加入（`player_service.rs:119-123`）。
- **「开放 / 隐藏」题目是选手可见性的唯一开关**：`jeopardy_event_challenges.hidden`（`packages/sdk/src/entity/jeopardy_event_challenges.ts:1-6`）经 `hidden/open` 接口翻转（`admin/event_challenges.ts:64-99`），选手端只收到 `hidden=false`（`player_service.rs:266-271`）。
- **封禁有两套、不要混用**：赛事级封禁是 `event_users.banned` / `event_teams.banned`（`client.admin.event_users.banned`、`client.admin.event_teams.banned`）；AWD 另有队伍 ban 记录（`client.awd.admin.banTeam` / `unbanTeam`，`packages/sdk/src/api/awd.ts:346-369`），选手端 AWD `banned` 用的是后者（`apps/api/src/modules/event/awd/api/player.rs:563-570`）。**只封 `event_teams.banned` 不一定让 AWD `banned` 变 true。**
- **柯里化签名要看清**：`fetch(event_id)` / `remove(event_id)` / `create(event_id)` 这类返回函数再返回 async 函数（`admin/event_users.ts:7-16,31-38`、`admin/event_teams.ts:7-20`、`admin/event_announcements.ts:7-49`），而 `banned`/`unbanned` 是普通对象参数。新前端的 API 封装层要按真实签名调用。

**要点**

- **AWD 管理端的状态机是「status 驱动」，不是「phase 驱动」**：Deploy/Precheck/Start/Pause/Resume 的可见性全部按 `AwdEventStatus` 判定（`ops.tsx:195-270`），而选手端和防火墙看的是 `phase`（`hardening/attack/pause`）。两套字段来自同一张 `awd_events` 表（`packages/sdk/src/entity/awd_events.ts:1-39`）。
- **`finish` 在 Default 里没有按钮**（`ops.tsx:224` 注释）。矩阵把 `finish` 列入 required 是因为 SDK 暴露了 `client.awd.admin.finish`（`awd.ts:314-317`）；新前端要实现它必须自己给出「何时可结束」的判定（后端会校验状态）。
- **必须用 `expected_updated_at` 做乐观锁**：`updateConfig` 的 PATCH body 需要它（`awd.ts:31`），Default 从 `config.updated_at` 取值（`configure.tsx:196-200`）。并发编辑时后端会拒绝而不是静默覆盖。
- **预检报告的 `error_msg` 是 JSON 字符串**，不是结构化对象（`awd.ts:147-151`）；parse 失败时必须降级显示原文（Default 的做法，`ops.tsx:28-40`）。
- **网络 `locked` 之后不可再分配**（`admin.rs:1014,1035-1038`）——UI 必须在 locked 时隐藏/禁用重新分配，而不是让用户点出一个必然失败的操作。
- **`client.awd.admin.resetGamebox` 是 specialized 行**（矩阵第 192 行，Default 无页面）：SDK 存在该方法（`awd.ts:337-345`），后端端点在 `apps/api/src/modules/event/awd/api/admin.rs:582`。本文不展开。

- **AWDP 配置的「Break 时长」是推导值**：`fix_duration_secs` 由管理员配，Break = 赛事总时长 − Fix（`configure.tsx:100-113`），提交时不发 `break_duration_secs`。要改 Break 只能改赛事 `start_time/end_time` 或 Fix 时长。`break_score` 默认按 `fix_round_score × 0.6` 联动（`:80-81,120-123`）。
- **`phase !== "pending"` 后配置不可改**（`configure.tsx:154`），与 AWD 的「按 status 集合判定」是不同口径。
- **`preparing_fix` 在管理端 UI 里没有专门展示**（`PHASE_META` 只列 4 个值，`ops.tsx:15-23`），但它确实会在 `break → fix` 之间出现（`apps/api/src/modules/event/awdp/service/event_service.rs:23-65`）。新前端应显式处理它，否则会短暂显示错误阶段。
- **`breakToFix` 会重置所有实例**（`runtime_generation + 1`，`ops.tsx:123-125`），但 Default **没有二次确认**——这是容易造成运维事故的点。
- **管理端 AWDP 的实例视图默认走归一化实例表**：这是 CAPABILITY-MATRIX 明确修正过的口径（见该文档 `## Verification` 的修正表）。

## 跨域公共语义

> 本章集中记录**反复出现**的判定。每条都给了 `文件:行号` 证据，实现新前端时应先按这些语义搭好「基础层」（客户端 / 会话 / 权限判定 / 分页 / 三态），再写各域页面。

### 1. 响应契约：HTTP 200 + `code !== 0` 与「非 2xx」是两条独立错误通道

平台的 handler **总是以 HTTP 200 返回 `UniResponse`**（`apps/api/src/api/response.rs:60-66` `HttpResponse::Ok().json(self)`），业务失败用 `UniResponse::err(code, message)` 表达（`response.rs:49-57`）；而 `?` 传播的 `AppError` 与 JWT 守卫失败走**真实 HTTP 状态码**（`apps/api/src/api/app_error.rs:104-117`：404/400/401/403/409/500），响应体仍是同一个 envelope（`app_error.rs:70-72`）。

| 通道 | 触发 | SDK 行为 | 新前端必须做什么 |
|---|---|---|---|
| 非 2xx（`http` / `network`） | `AppError`、守卫、网络失败 | 拦截器归一化为 `FloatCTFError` 并 **reject**（`packages/sdk/src/transport.ts:151-166`） | 处理 rejected promise；401 走 `onUnauthorized`（`transport.ts:157-163`） |
| HTTP 200 但 `code !== 0`（`platform`） | `UniResponse::err(...)` | **不会 reject**；`floatCTFErrorFromEnvelope` 只是导出，SDK 内部**无任何调用点**（`grep -rn "floatCTFErrorFromEnvelope" packages apps frontends` 只命中 `packages/sdk/src/errors.ts:145` 与 `packages/sdk/src/index.ts:42`） | **必须自己判 `res.code === 0`**（或调用 `floatCTFErrorFromEnvelope(res)`） |

- Default 只在 AWD flag 提交处显式判定（`frontends/default/src/routes/service/events/awd.$id/index.tsx:117-124`：`if (res.code === 0) ... else banner.showBanner("critical", res.message)`），**其余页面都忽略 `code`** —— 这是历史行为，不是可以照抄的正确做法。
- 成功码定义：`UNI_SUCCESS_CODE = 0`（`packages/sdk/src/protocol.ts:32`）；后端 `UniResponse::ok` 也用 `code: 0`（`apps/api/src/api/response.rs:26`）。
- 错误文案字段是 `message`（`response.rs:18`），**不是** `msg`；Default 的 `profile.tsx:52` 读 `data.msg` 属历史写法（对照 `packages/sdk/src/errors.ts:101-107` 只归一化 `message`）。

### 2. `EventInfo.joined` 与 `EventInfo.event.*` 的关系

- 形状：`EventInfo = {id, event: Events, joined: boolean, team_result?: {team, members[]}}`（`packages/sdk/src/types/eventInfo.ts:16-21`）。
- `joined` **不是** `events` 表的列，而是「当前用户在 `event_users` 里有没有行」：
  - 详情：`event_users::Entity::find_by_id((event_id, user_id))` → `is_some()`（`apps/api/src/modules/event/common/application/player_service.rs:196-199`）；
  - 列表：`list_events_for_user` 逐行扫 `event_users`（`player_service.rs:167-181`）。
- `team_result` **只有详情接口有**：列表接口硬编码 `team_result: None`（`player_service.rs:175-179`），详情才组装 `EventTeamResult{team, members[]}`（`:201-235`）。因此「我在哪支队」必须用 `client.service.events.get(id)`。
- `hidden` 与 `is_virtual`：玩家端列表 `WHERE hidden=false AND is_virtual=false`（`apps/api/src/modules/event/common/api/player.rs:39-40`）；详情 `hidden=true` → 404「未找到该赛事」（`player_service.rs:190-194`）。
- **`joined` 只是「报名」**，不等于「能看题目 / 能提交」：
  - 赛事题目列表额外要求「赛事已开始」→ 否则 400「赛事尚未开始」（`player_service.rs:250-255`），再要求 `joined` → 否则 400「你尚未加入本赛事」（`:257-264`）；
  - 题目的 `hidden=false` 过滤在同一接口（`:266-271`）。
- `joined` 与 `allow_join` / 时间的关系（服务端权威）：加入/退出/建队都要求 `allow_join=true` **且** `NotStarted`（`require_roster_mutable`，`player_service.rs:137-153`）；`purpose` 必须是 `competition`（`require_competition`，`:113-125`）。
- AWD 更进一步：`client.awd.player.status` 要求**队伍成员关系**，否则 403「你不是本赛事的参赛者」（`apps/api/src/modules/event/awd/api/player.rs:548-551`）。

### 4. 赛事家族（`family`）× 赛制维度如何决定进入哪个工作台

`Events` 上的三个维度（`packages/sdk/src/entity/events.ts:3-20`）：`family: jeopardy|awd|awdp`（`:15`）、`purpose: practice|competition`（`:16`）、`participant_mode`（`:17`）。**公共 TS 类型里没有 `mode` 字段**，能力矩阵的 Gaps 也确认 `Events` 不含 `mode`（`docs/frontend/CAPABILITY-MATRIX.md` §Gaps：「公共 TS 类型 `Events` 不含 `mode`」）。

- 合法组合由后端 `EventMode::validate`/数据库 check 约束（`apps/api/src/modules/event/common/domain/event_mode.rs:50-70`）：`jeopardy×practice×individual`、`jeopardy×competition×individual`、`jeopardy×competition×team`、`awd×competition×team`、`awdp×competition×team|individual`、`awdp×practice×individual`。
- **前端路由选择只看 `family`**（Default 做法）：`jeopardy → /service/events/jeopardy/$id`、`awd → .../awd/$id`、`awdp → .../awdp/$id`（`frontends/default/src/routes/service/events/index.tsx:36-66`）。管理端同理（`routes/admin/events/index.tsx:94-116`）。
- 能力位映射在后端 `EventCapabilities::for_mode`（`apps/api/src/modules/event/common/domain/capability.rs:22-60`）：Jeopardy → `supports_instances`+`supports_standard_flag_submission`；AWD → `supports_wireguard`+`supports_gameboxes`+`supports_rounds`+`supports_judge`+`supports_reset`（**无 instances**）；AWDP → `supports_instances`+`supports_gameboxes`+`supports_rounds`+`supports_judge`+`supports_reset`（**无 wireguard**）。
  - 该接口 `GET /api/events/{id}/capabilities` **SDK 未暴露**（Gaps class B；逃生舱 `client.serviceHttp.get("/events/<id>/capabilities")`，`packages/sdk/src/client.ts:80`）。新前端若需要，可**自行用 `family` 推导**（推断：capability 只由 `family` 与 `participant_mode` 决定，`capability.rs:23-58`）。
- `is_virtual=true` 的赛事只会出现在管理端（管理端详情页只给 Instance/Logs，`routes/admin/events/jeopardy.$id/route.tsx:54-68`），玩家端列表完全排除（`apps/api/src/modules/event/common/api/player.rs:39-40`），且不允许加入（`player_service.rs:119-123`）。
- **练习（`practice`）不走赛事报名**：`purpose !== competition` 时 join/team 一律 `UnsupportedForPurpose`（`player_service.rs:113-118`）；AWDP 练习走 Training Ground 的 `client.awdp.runs.*`（`packages/sdk/src/api/awdpRuns.ts:11-35`）。

### 5. Jeopardy 赛事题目 `open` / `hidden` 语义

- 权威字段：`jeopardy_event_challenges.hidden`（`packages/sdk/src/entity/jeopardy_event_challenges.ts:1-6`；同表还有 `points`）。
- 选手端：`GET /events/{id}/challenges` 只返回 `hidden=false` 的行（`apps/api/src/modules/event/common/application/player_service.rs:266-271`）——所以「隐藏」= **选手根本看不到这道题**，不是「可见但不可提交」。
- 管理端开关：`client.admin.event_challenges.open(...)` / `.hidden(...)`（`packages/sdk/src/api/admin/event_challenges.ts:64-99`）；Default 的行操作按当前 `hidden` 取反（`routes/admin/events/jeopardy.$id/index.tsx:113-136`）。
- 改分：`client.admin.event_challenges.setPoints({event_id, challenge_id_list, points})`（`admin/event_challenges.ts:37-51`），Default 要求 `> 0` 才可保存（`routes/admin/events/jeopardy.$id/index.tsx:218-257`）。
- **不要与挑战库的 `challenges.hidden` 混淆**：那是题目在**目录（`GET /challenges`）**里的隐藏位，管理端挑战页有单独的「隐藏」列（`frontends/default/src/routes/admin/challenges.tsx:76-85`）；赛事题目可用性由 `jeopardy_event_challenges.hidden` 决定。两者是不同表、不同语义。
- 选手端 `EventChallengeResult.{current_points, solved_count, solved, solved_no}` 里的 `current_points` 是**动态分值**（按已解出数计算），不是固定的 `event_challenge.points`（`player_service.rs:292-297`）。

### 6. AWD `phase` 全部取值与每相位的可用动作

枚举来源：`AwdPhase = hardening | attack | pause`（`packages/sdk/src/entity/sea_orm_active_enums.ts:28-32`）。

### 7. AWDP `phase` 与 `overview` 字段的对应关系

枚举：`AwdpPhase = pending | break | preparing_fix | fix | ended`（`packages/sdk/src/api/awdp.ts:13`；枚举定义 `packages/sdk/src/entity/sea_orm_active_enums.ts:50-56`）。

|---|---|---|---|---|

### 8. 管理员 vs 超管（`super_admin`）的接口差异

**本平台只有两个 JWT 角色守卫，没有第三个「admin」角色**：

- `UserJwtGuard` 要求 `claims.role == Role::User`（`apps/api/src/api/extractor/auth.rs:10-63`）；
- `SuperAdminJwtGuard` 要求 `claims.role == Role::SuperAdmin`（`auth.rs:18,65-96`）。

因此：

1. `POST /api/admin/session`（`client.admin.login`）签发的是 **`Role::SuperAdmin`** token（`apps/api/src/modules/identity/administrator/mod.rs:28,62`）。
2. `/api/admin/**` 下的端点全部用 `SuperAdminJwtGuard`——例：`dashboard.rs:135`、`docker.rs:50`、`database.rs:31`、`identity/user/mod.rs:100,164,248,294,310`（**管理用户 CRUD 也是超管权限**）、AWD 管理端（`awd.ts:276` 注释即写「管理端 AWD 生命周期（SuperAdmin）」）。
3. 结论（推断，依据上述两守卫与登录实现）：**「管理端登录」= 超管登录**；`client.admin.super_admin.*` 是超管**管理其他超管账号**的 CRUD（`packages/sdk/src/api/admin/super_admin.ts`），不是「更低权限的 admin」。
4. 前端含义：`adminToken` 与 `token` 是两个独立作用域（`FloatCTFAuthScope = "user" | "admin"`，`packages/sdk/src/transport.ts:40-41`），各自注入各自的 `Authorization` 头（`transport.ts:140-149`），401 也只清对应那个（Default：`frontends/default/src/api/client.ts:24-34`）。**不存在「用 admin token 访问选手接口」或反之的合法路径**。
5. 后端错误语义：超管 token 访问需要 `UserJwtGuard` 的接口会 401；选手 token 访问 `/api/admin/**` 同样 401（两个守卫都只认自己的 Role，`auth.rs:44-48,80-84`）。

### 9. 各列表接口的分页 `meta` 用法与 `QueryParams`

- 前端类型（公共）：`QueryParams = {offset?, limit?, page?, total?, filter?}`；`UniResponse<T> = {code, message, data?, meta?}`（`packages/sdk/src/protocol.ts:15-29`）。
- 后端同构：`QueryParams {offset, limit, page, filter, total}`，`UniResponse.meta: Option<QueryParams>`（`apps/api/src/api/response.rs:5-21`）；`meta` 由 handler 显式用 `UniResponse::ok_meta(data, meta)` 填充（`response.rs:34-41`）——**不是所有列表接口都填 `meta`**，`meta` 缺失时必须能降级。
- **请求侧**：Default 只发 `{page, limit, filter}`（`frontends/default/src/components/Table.tsx:157-163`），`limit` 可选 10/20/50/100（`:558-568`），页码从 1 起（`:605-611`）；`staleTime` 默认 30s，可用 `staleTime={0}` 强制每次挂载重取（`:102,122,162`，实例页用法 `routes/service/instances.tsx:179`）。
- **响应侧**：Default 只读 `meta.total` 作总条数，并在缺失时回落 `1`（`Table.tsx:298`）；它**不使用** `meta.page`/`meta.limit`（类型声明见 `Table.tsx:41-44`）。
- `filter` 是**服务端 DSL**，不是全文搜索：
  - 每个域注册自己的 `FilterMapping` 白名单（例：玩家赛事 = `id/title/family/allow_join`，`apps/api/src/modules/event/common/application/player_service.rs:823-850`）；
  - 多个条件用**逗号**分隔（Default 拼法：`${userFilter},author_id:<uuid>`，`frontends/default/src/routes/service/discussions/my.tsx:141-148`）；
  - `id`/`allow_join` 这类按精确匹配、`title`/`name` 是 contains（`player_service.rs:827-843`）；
  - **不在白名单里的键不会报错，只是被忽略**（推断，依据 `apply_filters` 按 mapping 查表的行为；因此前端筛选失效时应先核对白名单）。
- 无分页的列表同样存在：`client.service.solves.getTop15Users()` 无参数（`packages/sdk/src/api/solves.ts:23-26`）；Default 用 `disablePagination` 关掉分页 UI（`routes/service/top.tsx:65-70`）。管理端 settings 也 `disablePagination`（`routes/admin/settings.tsx:279`）。

### 10. 会话与实时通道的通用接线

- SDK **不持有 token**：`getUserToken` / `getAdminToken` 是同步纯读回调（`packages/sdk/src/transport.ts:65-68`），持久化归前端（Default 用 Zustand `persist` → `localStorage["auth-storage"]`，`frontends/default/src/stores/AuthStore.ts:16-33`）。
- 401 → `onUnauthorized({scope, status, error})`（`transport.ts:151-166`），前端按 scope 清对应 token 并决定跳转（`frontends/default/src/api/client.ts:24-34`）。
- SSE 用 `client.sse.connect`（user token）/ `connectAdmin`（admin token），路径相对本实例 base URL 解析（`packages/sdk/src/client.ts:96-102,131-145`）；Bearer 走 `Authorization` 头而非 URL（`packages/sdk/src/sse/connectSse.ts:1-12`）；401/403 停重连，退避 1s→30s + 0.3 抖动（`connectSse.ts:66-70`）。
- 四条真实流的路径（Gaps class B，非 React 前端需自行拼接）：`/events/{id}/awd/stream`（`packages/react/src/useAwdEventStream.ts:161`、`useAdminAwdEventStream.ts:136`）、`/events/{id}/awdp/stream`（`useAwdpEventStream.ts:131`）、`/service/awdp/runs/{runId}/stream`（`useAwdpRunStream.ts:112`）。
- 通用模式 = **SSE 失效 + REST 轮询回退（互斥）**：连上停轮询、断开用 15s 轮询（`useAwdEventStream.ts:126-146`）；事件只用来 `invalidateQueries`，真实数据永远来自 REST（`packages/react/src/awdInvalidation.ts:1-10`）。

### 11. 三态与破坏性操作的统一口径

- 列表三态（Default 口径，可参考实现）：`isLoading` → spinner；`data?.data ?? []` → 空表；mutation `onError` → `banner.showErrorBanner(error)`（`frontends/default/src/components/Table.tsx:298-303,334-336`）。**矩阵要求每项能力都处理三态**，因此新前端的列表组件必须至少能区分「加载中 / 空 / 失败」。
- 破坏性操作在 Default 里有三种处理，新前端必须逐项确认（不是统一规则）：
  1. **有确认对话框**：`GenericTable` 的批量删除（`components/Table.tsx:640-658`）、AWD 选手 Reset GameBox（`routes/service/events/awd.$id/gameboxes.tsx:120-128`）、AWD 管理端归档 / 令牌轮换（`routes/admin/events/awd.$id/ops.tsx:258-266,279-287`）、AWDP 管理端结束赛事（`routes/admin/events/awdp.$id/ops.tsx:95-103`）、AWD 赛事网络重新分配（`routes/admin/events/awd.$id/network.tsx:437-443`）。
  2. **无确认、直接执行**：选手销毁实例（`routes/service/challenges/$id/index.tsx:158-167`、`routes/service/events/jeopardy.$id/instances.tsx:79-87`、`routes/service/instances.tsx:146-154`）、删除评论（`routes/service/discussions/$id.tsx:361-363`）、退出赛事/战队（`routes/service/events/jeopardy.$id/index.tsx:192,254-268`）、AWD 管理端分数调整（`routes/admin/events/awd.$id/ops.tsx:396-401`）、封禁/解封（`routes/admin/events/jeopardy.$id/users.tsx:87-110`）、AWDP 管理端 `breakToFix`（`routes/admin/events/awdp.$id/ops.tsx:86-91`）。
  3. **SDK 有方法但 Default 无 UI**：`client.awd.admin.finish`、`client.awd.admin.resetGamebox`、`client.awdp.player.startInstance/stopInstance/getInstance`、`client.awd.player.*` 之外的部分 AWD 管理方法（见各章「要点」）。
- 新前端的破坏性操作**应当**提供自己的确认/二次确认（平台级只要求「语义不变」，不要求沿用 Default 的确认与否；但把「无确认」当成默认可接受是有风险的，尤其涉及 `breakToFix`、退赛、重置、计分调整）。
